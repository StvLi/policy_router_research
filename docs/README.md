## 0. 一句话

用户设想：用 **语言 embedding 聚类** 得到每个任务的 N 个子任务，用 **VAE** 把 `[图像, 机械臂状态]` 的历史映射到潜空间，用 **KS 检验** 判断当前潜状态是否符合某子任务的分布，据此在「子任务 prompt / 总任务 prompt / CAP 兜底」之间路由；期望在成功率上超过前两者、在墙钟上超过全程 CAP。

**评审结论：设想的方向（把"何时该换语言条件"变成一个可统计的判别问题）有价值，且可执行。**

**用户决议后的口径（`DECISIONS.md`）**：步骤 2 照原样（句向量 K-means，得 S1 语义簇，配 VLM 接地自洽）；步骤 3 照原样（V1，≈350 个 VAE）；步骤 4 **换成 conformal p 值**（KS 只做诊断）。

**已完成的判决实验（`G2_RESULT.md`）**：只用关节状态、不训 VAE，子任务可分性 balanced accuracy **83.4%**（任务不相交切分，k=5，随机 20%）→ **go/no-go 的"不可分"风险解除**。

## 1. 一页结论：哪些主张站得住

| # | 用户的三条主张 | 可行性 | 判定依据 | 详见 |
|---|---|---|---|---|
| A1 | 比「每步 VLM 生成 prompt 再注入 VLA」SR 更高 | **可比，但对手已变强** | 900 局实测：`T+Vnow`=7.00%（**显著有害**，p=0.020）、`T+Vnow-int10`=9.22%（与 T 打平）。**对手是 int10 而不是 Vnow**，要赢的是"打平"而非"负增益" | PRIOR_RESULTS §1、04 R6 |
| A2 | 比「只给总任务 prompt」SR 更高 | **最难，已被测两次且都是负/零** | ① 单任务 oracle 注入 60% vs 64%（无增益）；② **900 局：chunk 级显著有害、step 级打平**。真实基线是 **9.56%**，不是 64–84%——后者是单任务选择偏差 | PRIOR_RESULTS §2.1–2.2、04 R6 |
| A3 | 比全程「GPT6 Astra 做 CAP」墙钟更短 | **真但空洞，且已失去价值** | CAP **39.86 s/次**、全程 ≈ 72 min/集 = 150×。**但 900 局实测：VLM 只占墙钟 +3.8%，瓶颈是仿真步进（1.9 step/s·env）** → "少调 VLM"最多省 3.8%，而 `T+Vnow` 也早已比 CAP 快。**效率不能作为本项目的贡献** | PRIOR_RESULTS §2.4、04 R13 |
| A0 | （隐含）KS 检验可用作"不可信度" | **不成立** | 高维 + 时序自相关，KS 的 p 值会退化为恒 0/恒 1，需换 conformal p 值或能量距离 | 02 §4、04 R1 |
| A0' | （隐含）文本 K-means 给出"子任务" | **不成立（按字面）** | 实测：拿 f35 的 caption 做球面 k-means，k=4/5 退化成 pick/place/move/handover 的**动词族**；集内子任务 96.8% 不重复（是时序相位），跨集才重复（是语义类）。二者不是一回事 | 02 §2、04 R3 |

**因此本方案真正的卖点必须再收窄一次**（`PRIOR_RESULTS` §5）：效率没了，所以只剩 SR 与 OOD。

- ~~更好的 prompt 内容~~ —— 已被 ⑤ 档与 900 局双重证伪；
- ~~少调 VLM 换墙钟~~ —— 只值 3.8%；
- ✅ 还剩两条：**① 判别"该刷新什么"而不是"生成什么"**（现有实验注入的是在线 VLM 现推的有噪句子，token-F1 只有 0.608）；**② 判别"何时放弃语言、升级出去"**（全库 9.56% 意味着大量失败根本不是语言问题）。

**第三件必须先做的事**：现有数据把"刷新频率"与"动作视界截短"混淆了（`04` R14），而"何时切换"正是我们唯一还握在手里的旋钮。**G2.5 解耦实验的优先级高于 VAE。**

## 5. 术语表

| 术语 | 本方案中的定义 |
|---|---|
| **子任务 / subtask** | 一个时间上连续、语言上可命名、语义上单一的操作片段。**本方案区分两种含义，见 `02` §2**：语义类（semantic class）与时序相位（temporal phase） |
| **相位 k** | 集内第 k 个时序阶段（k 单调递增），路由真正需要的对象 |
| **潜空间编码器 F** | 把 `(o_{t-h:t}, q_{t-h:t})` 映射到 `z ∈ R^d` 的网络（用户原案为 VAE） |
| **典型性/不可信度** | 当前 z 与某子任务 z 群体的"不像"程度；本方案用 **conformal p 值**（越大越可信），取代 KS |
| **路由** | 由 p 值做出 `subtask → task → CAP` 三路决策 |
| **臂 / arm** | 一个闭环对照配置，命名沿用 `E-<vla>@<步>-<prompt模式>-<task>-L<n>` |
| **CAP** | Code-as-Policies：让强模型直接写/调技能代码执行，慢但泛化强。**待确认是 CaP 还是别的含义，见 Q1** |
| **墙钟 / wall-clock** | 单集端到端耗时（含仿真、VLA 推理、VLM 调用），单位 s/episode |

## 6. 命名提案（待并入 `NAMING.md`）

沿用既有三段式，新增两类对象：

```
潜空间编码器   lat-<数据>-<编码器>-<维>        例: lat-f35-r18-32
路由策略       rt-<数据>-<检验>-<N>            例: rt-f35-conf-9   (conformal, N=9)
评测 cell 的新 prompt 模式
               T+R      = 总任务 + 路由到的子任务 prompt
               T+R+cap  = 追加 CAP 兜底
```

评测 cell 示例：`E-vla-f35-6c-4g@15k-T+R-sb-L25`。
